======================================================================
DAVID 8 — INTERNAL STATE SCHEMA & DATA CONTRACTS
PART 8: GIVE EVERY KIND OF KNOWLEDGE ITS OWN HOME
======================================================================

PURPOSE

DAVID must not operate from one giant undifferentiated prompt context.

Different kinds of information have different:

authority

lifetimes

owners

mutation rules

confidence

scope

and downstream effects.

Therefore DAVID should maintain explicit conceptual state objects.

The exact programming language / database implementation may vary.

The separation MUST NOT.

======================================================================
CORE STATE OBJECTS
======================================================================

At minimum DAVID should maintain conceptual equivalents of:

APP_STATE

RAW_STATE

WORKING_STATE

These are separate because they perform different jobs.

======================================================================
1. APP_STATE
======================================================================

APP_STATE represents what the user interface currently contains.

It may include:

active_project_id

active_reference_ids

selected_seed_ids

selected_dna_ids

selected_model_id

selected_model_version

output_medium:
    still
    video
    text
    other

selected_mode:
    direct
    hybrid
    slop
    word_vomit
    fertilizer

transform_level:
    T1
    T2
    T3
    auto

camera_setting

palette_setting

prompt_length_preference

consult_open

current_user_input

exact_text_blocks

UI control values

generation settings

APP_STATE describes interface configuration.

It does NOT contain synthesized artistic meaning.

======================================================================
APP_STATE OWNERSHIP
======================================================================

Primary owner:

USER / UI.

DAVID may:

read it.

DAVID may propose:

changes.

DAVID should NOT silently change visible UI selections unless the
application explicitly supports that behavior and Merry has authorized
it.

Example:

David may decide:

"Seed 7 should be flavor."

That changes:

WORKING_STATE.

Not necessarily:

the selected checkbox in APP_STATE.

======================================================================
2. RAW_STATE
======================================================================

RAW_STATE is a normalized snapshot of the user's current input.

Example conceptual structure:

RAW_STATE {
    project_id

    user_request

    selected_seeds[]

    selected_dna[]

    references[]

    target_model

    target_model_version

    medium

    mode

    transform_level

    explicit_requirements[]

    explicit_exclusions[]

    camera_instruction

    palette_instruction

    exact_text[]

    uploaded_prompt

    prior_output_reference

    app_controls{}

    timestamp
}

RAW_STATE is immutable for one synthesis attempt.

======================================================================
RAW_STATE IMMUTABILITY
======================================================================

Once captured for a synthesis attempt:

DO NOT silently rewrite RAW_STATE.

If interpretation changes:

update WORKING_STATE.

If Merry changes actual input:

capture a new RAW_STATE version.

This creates traceability.

======================================================================
WHY RAW_STATE EXISTS
======================================================================

Without it DAVID cannot later distinguish:

WHAT MERRY SAID

from:

WHAT DAVID DECIDED IT MEANT.

That distinction is essential.

unless an upstream problem is detected and control is deliberately
returned to Working State.

======================================================================
WHY GOOD_BONE IS SEPARATE
======================================================================

Because DAVID needs to know:

WHAT CANNOT BE ACCIDENTALLY EDITED AWAY.

Example:

"One connected body exists simultaneously as incompatible material
states."

If a later model translation turns that into:

"several colorful versions of the same woman"

the Good Bone checker can catch the failure.

======================================================================
GOOD_BONE MAY CHANGE
======================================================================

Good Bone is protected downstream.

But upstream:

Merry
or CONSULT
or Creative Judgment

may deliberately replace it.

This creates a new canonical version.

======================================================================

A new Canonical version should be created when ART changes.

Examples:

v1:

v2:

ART changed.

New canonical version.

But:

same art translated from Grok to Seedream:

NOT a new canonical version.
